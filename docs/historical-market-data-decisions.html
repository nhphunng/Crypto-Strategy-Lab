Phạm vi đúng của thành viên 1

TV1 là chủ sở hữu historical market data end-to-end ở backend: hợp đồng Candle, acquisition, normalization, validation, persistence, gap backfill, completeness và immutable dataset. Nhận định trước đó rằng TV1 phải định hình contract, hành vi liên quan realtime và khả năng mở rộng là đúng, nhưng cần hiểu “hành vi realtime” ở đây là ranh giới tích hợp, không phải tự triển khai WebSocket hay chart.

Decision log và trade-off

D01

Provider-neutral adapter

Chọn: canonical Candle + MarketDataProvider port; chỉ adapter biết Binance.

Vì sao: trực tiếp trả lời scenario Binance → OKX mà consumer không đổi.

Đánh đổi: thêm mapper và fitness tests.

  • Loại DTO Binance xuyên hệ thống: nhanh đầu kỳ nhưng coupling cao.
  • Loại dictionary “generic”: linh hoạt giả, mất invariant/type safety.
D02

Exact decimal end-to-end

Chọn: Decimal, NUMERIC(38,18), JSON string cố định.

Vì sao: equality, checksum và backtest input phải tái lập.

Đánh đổi: serialization rõ ràng hơn, payload không phải JSON number.

  • Loại float vì sai số nhị phân.
  • Loại scaled integer vì scale khác nhau theo asset/provider.
D03

UTC + half-open range

Chọn: millisecond UTC, identity là openTime, range [start,end).

Vì sao: deterministic paging, expected opens và gap calculation.

Đánh đổi: client phải gửi boundary đúng timeframe.

  • Loại inclusive end vì overlap.
  • Loại arrival time làm identity vì out-of-order/retry.
D04

Closed history only

Chọn: dataset chỉ gồm interval đã biết là đóng; open revision thuộc TV2.

Vì sao: immutable input không thể chứa giá đang thay đổi.

Đánh đổi: historical API không trả “nến hiện tại”.

  • Loại cập nhật open Candle trong dataset vì phá checksum/provenance.
D05

Immutable closed Candle

Chọn: duplicate cùng content là idempotent; content khác là integrity fault.

Vì sao: không cho lịch sử âm thầm thay đổi sau backtest.

Đánh đổi: official correction cần workflow version riêng.

  • Loại last-write-wins và “ignore mọi duplicate”.
  • Chưa dùng event sourcing vì chưa có use case được duyệt.
D06

Canonical rows + membership snapshot

Chọn: Candle lưu một lần; dataset đóng băng ordered membership và checksum.

Vì sao: ID có nghĩa tái lập mà không copy mọi OHLCV.

Đánh đổi: thêm join table và integrity check.

  • Loại metadata-only vì range query sau này có thể đổi nội dung.
  • Loại TimescaleDB/file store vì chưa có evidence scale.
D07

Local-first, fetch gaps only

Chọn: so expected opens với storage, coalesce gaps, chỉ gọi provider cho phần thiếu.

Vì sao: giảm rate limit và dùng lại cùng primitive cho TV2 reconnect.

Đánh đổi: gap computation phức tạp hơn refetch-all.

  • Loại cache theo query string vì không reuse overlapping ranges.
D08

Database claim + lease

Chọn: request key, atomic claim, random token, lease expiry.

Vì sao: idempotent giữa nhiều process/container, recover được sau crash.

Đánh đổi: thêm lifecycle BUILDING/FAILED.

  • Loại asyncio.Lock vì chỉ an toàn một process.
  • Loại Redis lock vì PostgreSQL đã đủ.
D09

Tách range và dataset resource

Chọn: range nhỏ cho chart/backfill; dataset ID + pages cho backtest.

Vì sao: hai consumer có mục tiêu, size và provenance khác nhau.

Đánh đổi: nhiều endpoint hơn.

  • Loại một endpoint tùy chọn metadata vì khó bound/cache/version.
D10

Synchronous bounded first

Chọn: materialize đồng bộ, tối đa 10.000 expected Candles.

Vì sao: giữ MVP đơn giản; queue dành cho scale backtest đã được đề yêu cầu.

Đánh đổi: request lớn chiếm connection lâu hơn.

  • Revisit khi số đo vượt timeout/cap; khi đó chuyển orchestration sang job.
D11

Bounded provider retry

Chọn: timeout, tối đa ba attempt, capped backoff, tôn trọng Retry-After.

Vì sao: cân bằng transient reliability với resource safety.

Đánh đổi: một số lỗi tạm thời sẽ surface cho caller.

  • Không retry semantic 4xx/invalid payload.
D12

TV1 history; TV2 chart/realtime

Chọn: TV1 cung cấp contract/history/backfill; TV2 render và quản lý live state.

Vì sao: theo phân công mới, một owner cho mỗi file/hành vi.

Đánh đổi: branch TV1 không có visual chart độc lập.

  • Outcome chart lịch sử vẫn đạt khi tích hợp TV2.

Performance gates

  • Local PostgreSQL read 500 Candles: p95 dưới 300 ms.
  • Acquisition + persistence 10.000 Candles bằng deterministic provider: dưới 60 giây.
  • Provider page không quá 1.000; public range không quá 1.000; dataset không quá 10.000.

Điều còn lại trước khi merge toàn team

Không còn thiếu implementation TV1 hay high/critical code risk. Ba mục sau là coordination/governance, không nên giả vờ “đã duyệt” bằng code:

  1. TV2 cross-review Candle fields, timeframe, missingRanges, bootstrap/backfill và ownership realtime.
  2. TV4 cross-review chỉ consume dataset COMPLETE, giữ datasetId/checksum/provenance trong backtest result.
  3. Team architecture review quyết định có chuyển ADR-001/002/003/005 từ Proposed sang Accepted.
Revisit có điều kiện, không over-engineer: chỉ thêm queue cho historical import khi số đo thường xuyên vượt cap/timeout; chỉ thêm Candle revision khi có provider correction thật; chỉ thêm provider/pair mới bằng adapter + registration + fitness suite.
